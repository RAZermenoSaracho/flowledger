# database — Claude Code Guide

Contains the Prisma schema (single source of truth for the data model), all migrations, and the demo seed script.

See the root `CLAUDE.md` for monorepo-level constraints and the database change policy.

---

## What lives here

```
database/
  prisma/
    schema.prisma          # Single Prisma schema — PostgreSQL provider
    migrations/            # One directory per migration (auto-generated by Prisma)
      <timestamp>_<name>/
        migration.sql
    migration_lock.toml    # Managed by Prisma — do not edit manually
  seed.ts                  # Demo data seed script
```

---

## How to run migrations and seed

```bash
# From repo root:
npm run prisma:generate    # regenerate Prisma client after schema changes
npm run prisma:migrate     # apply pending migrations (dev mode, creates migration files)
npm run prisma:seed        # seed demo data (demo@flowledger.local / flowledger-demo)
```

After any `schema.prisma` change: run `prisma:migrate` (creates the migration SQL and applies it), then `prisma:generate` (regenerates the client). Both steps are required before the API can use the new schema.

## Schema naming conventions

| Thing | Convention | Example |
|---|---|---|
| Model names | `PascalCase` | `TransactionRelation`, `ProviderAccount` |
| Field names | `camelCase` | `createdAt`, `providerCredentialId` |
| Enums | `PascalCase` name, values `snake_case` | `AccountType { credit_card }` |
| IDs | `String @id @default(cuid())` | All primary keys |
| Money fields | `Decimal @db.Decimal(12, 2)` | `amount`, `shareAmount`, `initialBalance` |
| Soft deletes | `isArchived Boolean`, `archivedAt DateTime?` | `Account`, `Category`, `Group` |
| Timestamps | `createdAt @default(now())`, `updatedAt @updatedAt` | All models |
| Migration names | `<timestamp>_<short_description>` | `20260607120000_add_syncfy_integration_models` |

## Data model overview

Central entity: **`User`** — all data cascades on delete from `User`.

Core financial entities:
- **`Account`** — a financial account (manual or linked to a provider account)
- **`Category`** — personal (`groupId = null`) or group-scoped
- **`Transaction`** — income / expense / transfer; scoped to a user and optionally a group and account
- **`Group`** / `GroupMember` — multi-user collaboration unit (never "Household")

Shared expense flow:
- **`SharedExpense`** → **`SharedExpenseParticipant`** → **`SettlementRequest`**

Provider integration:
- **`ProviderConnection`** — a bank credential established via Syncfy
- **`ProviderAccount`** — a bank account imported from the provider; links to a user `Account` once confirmed
- **`ProviderImportedTransaction`** — staged transaction pending user review; becomes a `Transaction` on import
- **`ProviderWebhookEvent`** — audit log for all incoming webhook events (deduplication via `(provider, providerEventId)`)

Supporting:
- **`UserAuthAccount`** — OAuth provider mappings (Google, Syncfy user ID)
- **`TransactionRelation`** — directed link between two transactions (used for settlement payment pairs)
- **`Notification`** — in-app notifications

Full model details: `docs/DATA_MODEL.md`

## What to never do

- Edit migration `.sql` files by hand — Prisma manages these; manual edits break the migration checksum and will fail `prisma migrate deploy`
- Modify `migration_lock.toml` — managed by Prisma
- Apply schema changes by running raw SQL directly against the database — always go through `prisma migrate dev`
- Remove a migration directory that has already been applied to any environment
- Change a field name or type without a migration — Prisma will refuse to apply the schema unless a migration captures the change
- Use raw SQL (`prisma.$executeRaw`, `prisma.$queryRaw`) without explicit approval from the project owner
