## Context

`/v1` is an explicit allowlist (`v1.routes.ts`) of existing controllers behind `requireCredential` + `requireScope`; writes opt in to `auditV1Write`. MCP tools are registered in `registerTools`; write tools are only registered with the `write` scope and re-checked in `runWrite`, which also emits the audit line. Services already take `(userId, ...)` and enforce ownership in the Prisma `where`.

## Decisions

1. **Adapters only.** Every route wires an existing controller (REST) and every tool calls the same service (MCP). Controllers already read `req.user!.id`, which `requireCredential` populates. No new services, no migrations, no new scopes: reads need `read`, writes need `write`.
2. **Fewer tools via parameters.** `get_report` takes `type: summary | by_category | monthly_cashflow` plus the shared report filters. Archive and restore are one tool per resource, `set_account_archived` and `set_category_archived` with `{ id, archived: boolean }`, calling the existing `archive*`/`restore*` service. Currencies list is REST only; MCP only needs `get_exchange_rate`.
3. **Account/category delete mirrors the web UI.** Operator decision: API/MCP clients with `write` can do what the web UI can. Web path: `DELETE /accounts/:id` and `/categories/:id` (no extra middleware) -> `deleteAccountHandler` / `deleteCategoryController` -> `deleteAccount` / `deleteCategory`, returning 204. `deleteAccount`: `findFirst({ id, userId })` else 404 "Account not found"; no other guard (provider-linked and archived accounts included); `account.delete`. Schema effects: `Transaction.accountId` and `transferToAccountId` become null (a transfer keeps its other leg's account), `ProviderAccount.accountId` and `ProviderImportedTransaction.accountId` become null. `deleteCategory`: `getEditableCategory` (membership via `CategoryUser`, else 404 "Category not found"; group categories need group admin, else the group-admin error); `category.delete` cascades `CategoryUser`, and transactions/imported rows get a null category. Reused unchanged (same controller and service), so errors are identical; MCP surfaces the same message as an `isError` result. Tools carry `destructiveHint: true`, `idempotentHint: false` and tell the assistant to obtain explicit user confirmation.
4. **`DELETE /v1/transactions/:id` and `delete_transaction`.** Calls `deleteTransaction(userId, id)`, returns 204 (REST) or `{ deleted: true, id }` (MCP). MCP carries `destructiveHint: true`, `idempotentHint: false` (second call is 404). Behaviour verified in `transactions/services/delete.service.ts`: ownership is in the `findFirst` where; no block conditions exist; in one DB transaction it deletes the related notifications and then the row; the schema cascades the linked shared expense, its participants and their settlement requests; a settlement-generated payment transaction can be deleted, the settlement request keeps its status and its transaction link becomes null (`SetNull`); a transfer is one row, so deleting it removes both legs at once. The spec states these effects and tests assert them. The MCP description says so and tells the agent to confirm with the user first.
5. **Write input is re-parsed.** REST uses `validate(schema)`. MCP parses tool args with the same shared schema (z.object strips unknown keys), so non-route callers cannot mass-assign `userId`, `isArchived` or similar. Typed service params (lint change 2.2) make this checkable by the compiler.
6. **Caps.** New helper `utils/listCap.ts` (`capList(rows, 100)` returning `{ data, total }`) is applied by an adapter on lists whose services are unpaginated and unbounded: debts and imported transactions. Notifications are already `take: 50`. Accounts and categories are not new lists; they stay as documented small, user-created sets and are not capped here. Pagination parameters are not added.
7. **Audit.** REST: `auditV1Write(op)` on every new write route; the id capture is extended from `transaction.id` to `account.id`/`category.id`. MCP: all new write tools go through `runWrite`. One line per call, success or failure, no body.
8. **Read credential never mutates.** REST: `requireScope("write")` after `auditV1Write` (403 is audited, as today). MCP: write tools are not registered for read credentials and `runWrite` re-checks.
9. **Spec home.** MCP requirements go in a new capability `mcp-personal-tools`, because the `mcp-server` spec is not yet in the main specs.

10. **Parity round: imported review, notifications, profile (operator decision: web-user capabilities are the source of truth).** Adapters only, same controllers/services as the web routes, so authz, validation and errors are identical (non-pending import is `400`, foreign ids are `404` for single-row routes).
    - *Imported review.* Single-row REST routes reuse `patchImportedTransaction`, `postIgnore/UnignoreImportedTransaction` and `postImportedTransactionImport`. Batch routes reuse `postBatchIgnore/Unignore/Import` but validate with `publicBatchImportedSchema` / `publicBatchImportImportedSchema`: `selection.mode` must be `"ids"` and `ids` has 1 to 50 entries, so the web `filtered` mode (which resolves an arbitrary query to ids) cannot be used externally. MCP takes `ids[]` (same cap) and builds the ids selection itself. Batch semantics (verified in `update.service.ts` / `create.service.ts`): all rows are validated up front and any failure throws `400` with per-row `errors` and changes nothing; the import creation loop afterwards is sequential and not one database transaction; ids that are missing or owned by another user are dropped by `resolveImportedTransactionSelectionIds`, so a batch of only foreign ids returns count `0` instead of `404` (logged as KNOWN_ISSUES #021). Import is the web "Import" action: it needs write scope, is audited (`imported.import`, `mcp.import_imported_transactions`) and the MCP description tells the assistant to confirm with the user; it is not `destructiveHint` because nothing existing is lost, but it is not undoable except by deleting the created transaction.
    - *Notifications.* Unread count reuses `getUnreadCount`; mark-read routes reuse `markRead` / `markAllRead` with `notificationParamsSchema` on the path. MCP folds the count into `list_notifications` and adds `mark_notifications_read` (`{ id }` xor `{ all: true }`).
    - *Profile.* `GET /v1/me` reuses `getMe`. `PATCH /v1/me` validates the new `updateUserPreferencesSchema` (name, preferredCurrency, at least one) and calls the new thin `updatePreferences` service, which loads the current user and calls the unchanged `updateProfile` with the current email, so the login identifier cannot change. MCP `get_profile` / `update_preferences` use the same service. Email, password, plan, avatar and sidebar side stay web-only.
    - *Misc reads.* `get_transaction` calls `getTransactionById` (same as `GET /v1/transactions/:id`); `list_currencies` calls `listCurrencies`.
    - *Structure.* REST routes live in `v1.misc.routes.ts` (`v1MiscRouter`, mounted before the groups router); MCP tools in `tools.imports.controller.ts` and `tools.user.controller.ts`, the read tools in `tools.reads.controller.ts`.

## Risks

- Deletes are irreversible; account/category delete unlinks transactions (no guard, as in the web app) and transaction delete cascades shared-expense data. Mitigations: `write` scope only, audit line, `destructiveHint`, explicit description, rate limit.
- Retried creates duplicate (no idempotency). Documented, deferred.
- `updateAccount` can change `currency` on an account with transactions; behaviour is the same as the web app and is unchanged.
- Notifications may contain counterpart names; they are the credential owner's own rows.
- Batch import can create transactions for the first rows and then fail on a database error (no single database transaction); retrying is safe because processed rows are rejected (KNOWN_ISSUES #021).
- An API key or MCP token with `write` can import bank rows without a human click; same power as `POST /transactions`, mitigated by the audit line, the 50-id cap, no filtered mode and the confirmation wording.
