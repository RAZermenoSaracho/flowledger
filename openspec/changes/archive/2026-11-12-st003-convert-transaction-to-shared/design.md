# Design

## Context

Builds on ST-007 (shell, Details/Related tabs, create-time sharing, the `sharedExpense` shape on `updateTransactionSchema`, #017 guard) and ST-005 (`useFormDraft`, `FormView`, `EditableField`, `RelatedList`, Profile draft). No second form state machine, no second mutation pipeline.

## Four separate concepts

Each has its own state, rules and actor; none implies another.

1. **Ownership / edit rights**: only the transaction owner edits the transaction and the sharing structure (`ownerUserId`/`userId` in the Prisma `where`). A participant never edits.
2. **Allocation / proposal**: the owner's `shareAmount` per participant. Changing it is a proposal; it does not by itself create an obligation.
3. **Acceptance / rejection**: `acceptance` (`proposed|accepted|rejected`), set only by the participant (or by the system: block-time rejection, material-change re-proposal, manual = accepted).
4. **Settlement / payment**: `status` (`pending|partial|paid`), `paidAmount`, `SettlementRequest`. Unchanged, only counted for `accepted` shares, and the source of the edit guards.

## Decisions

- **Atomic save.** The Sharing tab edits the ST-007 draft. Save sends one `PUT /transactions/:id` with `sharedExpense: { enabled:false } | { enabled:true, title?, participants:[{id?, userId?|manualName?, share}] }`, applied in the existing `prisma.$transaction` through one tx helper `applySharedExpenseToTransaction(tx, ...)` in the shared-expenses module. Failure (400/409/network) leaves the server untouched; the draft is kept and Save retries. No partial-failure state.
- **One helper, every entry point.** `POST /transactions` (ST-007), `PUT /transactions/:id`, `POST /shared-expenses` and `PUT /shared-expenses/:id` all call it. `PUT /shared-expenses/:id` no longer deletes and recreates rows and ignores client `paidAmount`/`status`. Rows are diffed by `id`/`userId`; payment fields are server-owned.
- **Guards (all 400, field-addressable, server-side):** share >= `paidAmount` + pending requests; remove only if `paidAmount=0` and no pending request; unshare, delete shared expense and `DELETE /transactions/:id` blocked while any payment or pending/approved settlement exists; expense<->income flip and switching to `transfer` blocked when payments or pending requests exist; fully paid shares locked; sum of shares <= amount (ST-007 #017). `DELETE /transactions/:id` also keeps purging its notifications.
- **Duplicate conversion.** `SharedExpense.transactionId` is unique; the conflict maps to 409 "This transaction is already shared".
- **Consent as a column.** `acceptance` lives on the participant row, not a separate invitation model. Backfill: app-user rows `accepted`; manual participants always `accepted`.
- **Counting.** A single predicate (`acceptance = accepted`) is applied in debts read/totals, person balances, settlement requests and exposed for ST-008. `proposed` rows are listed as "awaiting acceptance" to both sides; `rejected` shown to the owner.
- **Re-proposal.** Raising a share or flipping direction on an `accepted` share -> `proposed` + `shared_expense_updated`. Lowering or non-financial edits keep `accepted`. `rejected` returns to `proposed` only when the owner changes its amount. The owner has no endpoint to set acceptance.
- **Notifications.** New types `shared_expense_invited/updated/accepted/rejected`; at most one unread per (recipient, sharedExpense, type), a newer replaces it. Suppressed from a blocked user to the blocker. For app users `shared_expense_invited` replaces `shared_expense_added`/`debt_owes_money` at proposal time.
- **Blocking.** `UserBlock(blockerId, blockedId)` unique pair. Block turns the blocker's `proposed` shares from the blocked user's expenses into `rejected`; accepted obligations, payments, settlements and Group membership untouched. Unblock restores nothing. Generic error "This user can't be invited."
- **Username.** Stored normalized lowercase with a plain `@unique` (case-insensitive by construction, no raw index SQL). Generated by one helper (`user_` + 12 random chars, retry on P2002) at both signup paths. Change through the existing own-profile update; the unique constraint decides races (P2002 -> 409 on the `username` field). Relations stay on `User.id`; the username is never authz or a credential.
- **Public shape.** `toPublicUser`/`publicUserSelect` -> `{ id, username, displayName|null }`; `displayName` is `name` only in `username_and_name`. Applied on users search, group members, debts, person balances, settlements, shared-expense owner/participants (app users live label, manual keep their name), new notification text. Old notification text stays (documented limitation).
- **Discovery.** `GET /users/search?q=`: exact username first, then prefix, q >= 3, max 10, no email/name matching, excludes self and blocks both ways, rate limited with `createRateLimiter`. `/v1` and MCP use the same service.
- **Universal sharing.** `normalizeSharedExpenseParticipants` accepts any non-blocked app user or manual participant on group and non-group transactions. Non-member participants get only the shared expense and a transaction summary (amount, date, title, own share), never Group data. `/v1` and MCP drop the non-group rejection.
- **Migration.** ST-003 owns the one B-004 migration. Backfill SQL (username assignment where null, acceptance `accepted`) is data SQL under the CLAUDE.md raw-SQL rule: the owner approves the migration SQL before it is applied. No other raw SQL.
- **UI.** Sharing tab uses ST-005 `RelatedList` in draft mode (participant, share cell, paid, acceptance badge, remove; footer allocated / owner's share / unallocated). Blocked users tab uses `RelatedList` in immediate mode. Debts "awaiting acceptance" and the notification target host accept / reject / "Reject and block". No new form or view; no approval dashboard.

## Risks / Trade-offs

- Username squatting and enumeration: bounded by reserved list, min-3 prefix, 10 cap, rate limit; exact-match revealing existence is accepted for discovery.
- Counting predicate must be applied everywhere debts are read; covered by a shared helper and an integration test.
- Old notification text may show a prior name/email-free label; accepted and documented.
- Larger change than one form; mitigated by task ordering and the single reviewed migration.
